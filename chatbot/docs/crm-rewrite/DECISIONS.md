# Implementation decisions

## Foundation (Agent A)

1. **Pre-registered class names.** `Plugin::controllers()` / `Plugin::services()` already list every controller/service named in ARCHITECTURE §2 / ROUTE-MAP (plus `SubscribeController`, `IntegrationsController`, `Integrations\FormCapture`, `Integrations\LeadsAutopilot`), guarded by `class_exists`, so parallel agents don't have to edit the same file. Both lists are also filterable.
2. **Services init on `init` priority 5**, so `query_vars`, shortcodes and cron schedules are registered before WordPress uses them.
3. **Base `Domain\Repository`** holds shared CRUD/hydration; concrete repositories only add their own queries. Unknown keys passed to insert/update are dropped (column whitelist).
4. **`templates.is_pro` column** added (§11.10 needs 2 Pro built-ins; §3 didn't list it).
5. **`messages.claim()` doesn't change status.** There is no transitional status in the spec; the Scheduler lock guarantees one runner, and a crash simply leaves rows `queued` for the next tick. `/campaigns/{id}/process` must take the same lock as the cron tick.
6. **Campaign delete** removes only the campaign's `queued` messages; sent messages and events are kept so global analytics stay correct.
7. **Upsert on an existing contact** fills only empty fields, merges attributes with existing keys winning, adds groups, and **never changes status**. A form or chatbot lead can't resubscribe someone who unsubscribed, or confirm a pending contact. Callers that really want a status change use `change_status()`, and imports with `update_existing` use `update()`.
8. **Double opt-in applies only to public sources** (`chatbot, shortcode, subscribe, form, cf7, wpforms, gravity, conversational`, filterable via `wpbot_crm/public_sources`). Admin create, imports and leads are not affected. `create()` never sends a confirmation email.
9. **Event logging inside ContactService**: new contacts log `subscribe`; `change_status` logs `unsubscribe` (→ unsubscribed) and `confirm` (pending → subscribed/customer). Tracking/feature code should not log these again.
10. **`confirmed_at`** is set at creation for contacts created as subscribed/customer, as well as on pending → subscribed.
11. **Single-brace merge tags** (`{first_name}`) are replaced only when the tag is known, and unknown ones are left untouched, so CSS/JSON braces survive. Unknown double-brace tags become ''. Extra tags available: `full_name`, `site_name`, `site_url`, `year`, and scalar custom attributes.
12. **Free monthly campaign limit** counts campaigns whose `created_at` falls in the current calendar month (site timezone). Deleting a campaign therefore frees a slot. Daily send cap counts only campaign messages (not automation emails) sent since local midnight.
13. **Settings**: the default footer interpolates the current year at runtime. Values that start with `••••` are treated as "unchanged" for API keys. Numerics are clamped to ≥1. Extra keys are only accepted if added through `wpbot_crm/settings_defaults`.
14. **Dates::iso() returns `null`** for empty dates, and **Dates::mysql() returns `''`** (templates need a string).
15. **Audience with `send_to=lists|tags` and an empty selection** resolves to nobody (`1=0`) rather than everyone. Group ids in excludes are merged, because lists and tags share one id space.
16. **`drop_all()`** also deletes `wpbot_crm_*` transients. Hooking it into `uninstall.php` (behind the "delete data" setting) is left to the lead engineer.
17. **Constructor nullable types** use the explicit `?Type $x = null` form (valid in 7.1+, avoids PHP 8.4 deprecation).

## Agent B

1. **Confirmation-email hook lives in `Mail\Tracking::init()`** (`wpbot_crm/send_confirmation` → `Mailer::send_confirmation`), because `Mailer` is not a registered service and Plugin.php must not change.
2. **Footer unsubscribe link is skipped when the body already contains `{{unsubscribe_url}}`** (all seeded templates do), so recipients never see two unsubscribe links. Footer text and company name/address are always appended. `{YEAR}` is replaced, and the footer also goes through `Personalizer`.
3. **The unsubscribe URL carries `&m={message_id}`** (in the body and in `List-Unsubscribe`), so the `unsubscribe` event is linked to the message. `m` is accepted only when the message belongs to the token's contact. The URL accepts POST from both the confirmation button and RFC 8058 one-click (`List-Unsubscribe=One-Click`).
4. **The open event is logged once per message** (first open only; `messages.opens` still counts every open). `wpbot_crm/email_opened` fires on first open only. Clicks log an event and fire `wpbot_crm/link_clicked` on every click. Dashboard `opened` therefore means unique opens per message; `clicks` means total clicks.
5. **Opens/clicks are recorded only while `track_opens` / `track_clicks` are on.** A validly signed click link always redirects, even when tracking is off. A bad signature gets a 400 page and no redirect.
6. **Link rewriting** skips non-http(s) hrefs (`mailto:`, `tel:`, `#…`), the unsubscribe URL and any link already containing `wpbot_crm=`. UTM params are added before click-wrapping and only when the link has no `utm_source` yet.
7. **Cron interval = max(60, `batch_interval`) seconds** (custom schedule `wpbot_crm_minute`, computed on each filter call so a settings change takes effect at the next reschedule). Tick wall time is 20 s.
8. **Recipients are enqueued in the tick, not in `send`**, so a scheduled campaign resolves its audience at send time. `send` returns `queued` = the current audience count. A `sending` campaign whose audience resolves to 0 at enqueue time is marked `failed`.
9. **`send_throttle` (emails/min) uses a per-campaign 60 s window stored in transient `wpbot_crm_throttle_{id}`.** There is no repository query for "sent in the last minute", and controllers/services must not run SQL.
10. **The tick claims messages per campaign** (`claim( $n, $campaign_id )`) and never sends queued automation rows. `AutomationEngine` sends those itself through `Mailer::send_to_contact`.
11. **Campaign counters `sent`/`failed`** are incremented by `Mailer` whenever `campaign_id` is in the context. List stats (`sent_count`, rates) come from `MessageRepository::stats_for_campaigns`.
12. **Campaign PUT** ignores `status` except `draft|paused`, and never changes a `sending|sent|scheduled` campaign. `send` on a `sent` campaign returns 409 ("Duplicate it to send it again"). `send` on a `sending` campaign is a no-op success. `duplicate` counts toward the free monthly limit.
13. **List rows omit `email_body`/`content`** to keep the payload small. `GET /campaigns/{id}` returns everything. Optional `scheduled_at` (site-local) is accepted on create/update; no UI sends it yet.
14. **Campaign/template HTML is stored raw for users with `unfiltered_html`**; for others it goes through `wp_kses_post`.
15. **SMTP**: GET/POST return 402 `wpbot_crm_pro_required` for non-Pro users. POST requires `smtp_host`. An empty or missing `smtp_password` keeps the stored one. `phpmailer_init` applies to all site mail while Pro is active and a connection is saved. It sets the transport, plus `Sender` (envelope) from the connection's `from_email`. The visible From still comes from the campaign or the CRM settings.
16. **Templates**: editing a built-in returns the new custom copy (new `id`), which keeps the original's `is_pro`. Built-ins may be deleted; the seeder re-adds them only on the next schema install/upgrade. Unknown categories map to `Marketing`. `type` is `system|custom`.
17. **Analytics `days`** is clamped to 1–365. `sent` counts every CRM message (campaigns and automations) sent in the window.

## Agent C

1. **Contacts GET** defaults to `per_page=100` (UI sends 100; max 500, `0` = all). Items carry `lists`/`tags` as `[{id,title,name}]` plus `list_ids`/`tag_ids` for convenience; an unknown `status` filter returns no rows instead of being ignored. `orderby`/`order` pass through to the repository whitelist.
2. **Contact create** uses source `manual`; an invalid `status` falls back to `subscribed` (create) but is a 400 on PUT. PUT with an empty `status` leaves the status unchanged. Only `list_ids`/`tag_ids` keys that are present trigger replace semantics.
3. **Bulk import writes directly** (multi-row `INSERT IGNORE` for contacts, memberships and `subscribe` events, 500 rows per batch) inside `Domain/ContactImporter` (no repository method exists for bulk writes). New contacts get **no per-contact hooks** (no `contact_created`/`group_added`, so automations don't fire for imports and nobody gets 20k welcome emails); one `wpbot_crm/contacts_imported( int[] $ids, string $source )` action per batch instead. 20,000 CSV rows import in ~2.2 s / ~200 queries locally.
4. **Import semantics**: `skip_test` defaults to true; invalid emails are always skipped; duplicates inside one file are skipped; existing contacts are counted as `skipped` unless `update_existing`. With `update_existing`, non-empty fields overwrite, a CSV `status` column changes the status (the import-wide `status` option applies to **new** contacts only, so an import can't resubscribe people), extra CSV columns are merged into `attributes` (max 30 keys, 500 chars), and the chosen lists/tags are **added** (never removed). Source labels: `csv`, `wordpress`, `woocommerce`. `set_time_limit(300)` + `wp_raise_memory_limit('admin')` where allowed.
5. **Test/disposable/role filters**: test = `example.*`, `test.*`, `domain.com`, `your*.com` placeholders, `localhost`, TLDs `.test .example .invalid .localhost .local`, or local parts like `test`, `fake`, `dummy`, `asdf`, `noemail`. Disposable list is ~110 hand-picked domains; role list is exactly §11.9. Both Pro-only (silently ignored for free).
6. **CSV upload** must pass `is_uploaded_file()` and have a `.csv/.txt/.tsv` name; a file without an `email` column returns 400 `wpbot_crm_no_email_column`. Delimiter/header mapping is the foundation `Support\Csv` (BOM-safe).
7. **WooCommerce import** = users with role `customer` (billing meta, falling back to the account email) followed by billing details of `processing`/`completed` orders (guests included), de-duplicated by email. Woo inactive → 400 `wpbot_crm_woo_inactive`.
8. **Groups**: PUT renames but keeps the slug (shortcodes that reference the slug keep working). `title` or `name` accepted on write; both returned. DELETE returns `{success,deleted,id}`. No `GET /lists/{id}` (UI doesn't use it).
9. **Automations**: `active` is accepted as an alias of `published`; unknown status → `draft`; unknown `trigger_name` → 400 (empty allowed). Steps route accepts `sequences` (or `steps`); UI aliases `add_list`/`remove_list` and `action_name`-less items with `type` are mapped; an unknown action → 400 "Step N: Unknown step type." Step ids: sent ids kept unless duplicated, others get max(old ∪ new)+1. Steps settings: `body`/`email_body` → `wp_kses_post`, `url` → `esc_url_raw` (http/https), the rest `sanitize_text_field`.
10. **Replacing steps re-points waiting runs by step id** (`AutomationEngine::remap_runs`): a run whose step was deleted moves to the next surviving step; if none survives it is completed.
11. **Engine**: zero-delay steps following the current one run in the same pass (max 20), so `wait(0)→send_email(0)` sends on the first tick. Runs of a **draft** (unpublished) automation are postponed 1 hour (paused, not exited). Missing contact/automation → run `exited`. `send_email` without the Mailer class → retried in 5 minutes. `send_email` to a non-sendable contact (not `subscribed|customer`) or with empty subject/body is skipped and the flow continues. Plain-text bodies (no tags) are `wpautop`ed; Mailer personalises. `step_key` = `step-{id}`. Mailer errors don't stop the flow (the message row records the failure).
12. **Step settings** (UI has no fields yet): tag/list steps read `tag_id|list_id`, else `tag|tag_name|list|list_name` (add creates the group, remove only looks it up); `update_contact` reads `field` (first_name, last_name, phone, company, website, status) + `value`; `webhook` POSTs `{event, automation{id,title}, step_id, contact}` (token removed) as JSON, timeout 10 s, blocking.
13. **trigger_config narrowing** (not sent by the UI): every key narrows by equality with the trigger context; `*_ids` keys compare to `*_id` (e.g. `group_ids` ↔ `group_id`), `url` matches by substring. Contexts: group triggers `group_id`; status change `status`,`old_status`; created `source`; opened/clicked `message_id`,`campaign_id` (+`url`); Woo `order_id`; users `user_id`; FormCapture whatever it passes.
14. **`user_registered` / `woo_order_completed` triggers** (engine hooks at priority 20, after the sync integrations at 10): if the email isn't a contact yet, it is created (source `wordpress` / `woocommerce`, Woo status `customer`) **only when a published automation listens to that trigger**; otherwise nothing is stored unless the sync setting is on.
15. **Settings**: `sync_wp_users` and `sync_woo_customers` (default false) are added by `Integrations\WordPressUsers` / `Integrations\WooCommerce` through the `wpbot_crm/settings_defaults` filter (no foundation change needed). `SettingsController` stores/returns every boolean-default key as a real boolean and rejects invalid `from_email`/`reply_to` with a 400.
16. **Woo sync** creates new buyers with status `customer` (sendable) and tag "Customer"; existing contacts keep their status (upsert rule) and get the tag.
17. **Subscribe route**: honeypot hits return the normal success message (nothing stored); the rate limit (10 per IP per fixed 10-minute window, `REMOTE_ADDR` only — proxies' `X-Forwarded-For` is spoofable) counts every nonce-valid attempt. `list`/`tag` accept id, slug or name (comma-separated allowed). Groups that don't exist are created **only** when the request carries the shortcode's HMAC `sig` (proves the site owner wrote the shortcode); otherwise only existing groups are joined. With double opt-in on, an existing `pending` contact gets the confirmation again and an `unsubscribed` one is moved to `pending` and sent a confirmation (only the confirm link resubscribes). Nonce failure → 403 "This form has expired…" (page caching can serve stale nonces).
18. **Shortcode** emits no global assets: the form plus one inline `<script>` (first form on the page only) via `wp_get_inline_script_tag`; screen-reader labels, `role="status"` live region, honeypot wrapper `aria-hidden` + `tabindex=-1`. Groups are not created at render time (no writes on page views).
19. **Size**: `Domain/AutomationEngine.php` (~580 lines) and `Domain/ContactImporter.php` (~450) exceed the ~400-line target; splitting them would need files outside C's ownership (e.g. `Domain/AutomationSteps.php`). Row generators for imports live in `Integrations\WordPressUsers::rows()` / `Integrations\WooCommerce::customer_rows()`.

## Agent D

1. **AI resolution order** (`Support\Ai::resolve()`): explicit `$opts` → CRM settings (`ai_provider`, its `<provider>_api_key`; `ai_model` only when that provider is the CRM's selected one) → WPBot's AI options for the same provider (same option names as `WPBot_Insights_Adapter::get_ai_import()`, read directly so the adapter needn't be loaded) → WPBot's active AI provider when the CRM provider has no key anywhere. Model falls back to the Insights `Providers` default. An explicit `$opts['key']` (even empty) never falls back.
2. **Insights loading**: if `QuantumCloud\Insights\AI\Provider_Client` is not loaded, `Ai` requires `includes/insights/src/autoload.php`; when that file is missing too, every call returns `wpbot_crm_ai_unavailable` (503) and `ai/test` returns 200 `{success:false}` with the same sentence.
3. **JSON mode**: always requested via `AI_Request` `response_format=json` (Insights applies it for OpenAI and Gemini only). Replies are parsed after stripping `<think>/<thinking>` blocks and ``` fences, falling back to the outermost `{…}`/`[…]` span.
4. **`ai/test` with a masked key** (`••••1234`, which is what Settings GET returns) tests the saved key for that provider. Empty model → provider default.
5. **`ai/generate-email`**: free sites silently get `professional`/`simple-html` for Pro styles/layout; unknown styles → `professional`. HTML is cleaned (drops `<head>/<style>/<script>/<iframe>`, comments, document wrappers) then `wp_kses` with the post allow-list + table/email attributes + `style` everywhere. If the model forgot them, a `Hi {{first_name}},` greeting and an `{{unsubscribe_url}}` link are added. Response also carries `style`/`layout` (the values actually used).
6. **Lead Finder routes are all Pro-only, including GET `leads/settings`** (contract §4 lists #38–43 as Pro). The free UI shows a lock screen and only logs the GET error.
7. **`wpbot_crm_leads` extras**: a `filters` sub-array (`industry, role, location, company_size, keyword`) for Option A; it is also filled when those keys are POSTed top-level. Stats (`total_leads, duplicates, bad_mx, search_depth, last_execution`) are ignored on POST and written only by the autopilot/reset. Keys `hunter_key, firecrawl_key, places_key, openai_key` are encrypted with `Crypto` and masked like Settings.
8. **Search query** = `"{keyword} {industry label} in {location}"`; dropdown industries map to plural phrases ("healthcare clinics"), `us/uk/ca/au` add a country code (`gl` for Serper, `region` for Outscraper, `regionCode` for Google). `company_size` cannot be filtered by any places API and is ignored. Social/directory hosts (facebook, yelp, linktr.ee…) are skipped as company domains.
9. **Provider details coded defensively** (fields per public docs; unknown fields ignored): Serper `POST /places {q, gl, page}` → `places[].title/website/phoneNumber/address`; Outscraper `GET /maps/search-v3?query&limit=20&skip&async=false` → `data[0][].name/site/phone/full_address`; Google Places Text Search (New) with a field mask, paging by `nextPageToken` (page N costs N requests, capped at page 5); Hunter `domain-search` (limit ≤ 10); Firecrawl `POST /v1/scrape {formats:[markdown,links]}`. Endpoints are class constants.
10. **Role → Hunter filters**: founder → seniority `executive`, department `executive`; marketing_vp/sales_vp/hr_director → `senior,executive` + marketing/sales/hr; it_manager → `senior` + it. If the filtered call finds nobody, one unfiltered call is made; free-text roles rank results whose position contains the text first.
11. **Firecrawl fallback** scrapes the homepage, then `/contact`, and keeps only addresses on the company's own domain, or a webmail address (gmail, outlook…) when the site has none of its own. Obfuscations like `name [at] domain` are decoded. No names/titles are guessed.
12. **MX**: `getmxrr` (else `checkdnsrr MX`, else assume valid), cached per domain for a week in transient `wpbot_crm_mx_{md5}`; filter `wpbot_crm/leads/pre_mx_check` can short-circuit (tests). Bad-MX and already-in-CRM emails are counted (`bad_mx`, `duplicates`) and dropped.
13. **Search bounds**: up to 3 emails per domain, up to 5 places pages per call, 50 s budget (filter `wpbot_crm/leads/time_budget`), `limit` capped at 100 for the UI and 200 for autopilot. Bad key / quota errors (401/403/402/429) stop the search; if some leads were already found they are returned, otherwise the error is. Other per-domain errors skip that domain.
14. **Import**: emails already in contacts (or repeated in the payload) count as `duplicates` and are left untouched; invalid rows are counted in an extra `skipped` field. New contacts are `subscribed`, source `lead_finder`; `title, location, domain, linkedin` go into `attributes`.
15. **Autopilot**: Option A uses saved `filters` (or a simple "X in Y" parse of `ai_prompt` when no filters are saved); Option B uses `Ai::json` with the Lead Finder `openai_key` (OpenAI, gpt-4o-mini) when set, else the CRM AI settings; if no AI is configured at all it falls back to the same simple parse. Volume: number in `auto_volume`, or `custom_auto_volume` for "Custom Number". The pointer advances to the page after the last one read; when the provider returns an empty page the pointer resets to "Page 1". `last_execution` uses the site's date/time format. A 5-minute transient lock prevents overlapping runs (409 `wpbot_crm_leads_busy`). The daily event is scheduled 5 minutes after it becomes enabled and only while `is_autopilot_enabled` **and** Pro; it is reconciled on every `init` and on settings save.
16. Extra helper classes in `Domain/Leads/`: `LeadSettings`, `ApiClient` (JSON HTTP + friendly errors), `PlacesClient`, `EmailFinder`, `MxChecker`, `LeadFinder`, `LeadImporter`.
